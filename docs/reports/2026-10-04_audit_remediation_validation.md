# RelayFS audit remediation and validation — 4 October 2026

The reproducible defects in both final audits have been corrected and regression coverage added. This is a **controlled-validation handoff**, not an unconditional approval to use irreplaceable data. Version checks and retained recovery copies substantially reduce destructive behavior; pCloud and ordinary Android filesystem operations do not provide an atomic compare-and-replace contract against external writers. That remaining limitation and the live-device acceptance gates are described below.

Scope: the working tree based on `4ce76bcfb647b0bd6b9a900a0a4bca83470e45db`, including the user's existing uncommitted changes. No live pCloud account, installed app, or real user document was changed. Verification uses temporary files, synthetic Room databases, fake providers, Robolectric, and MockWebServer. No commit was created.

## Review of the other agent's report

The original [pre-production audit](2026-10-04_pre_production_final_audit.md) is retained as historical evidence, with review corrections at the top. Its findings 1, 2, and 4–9 are valid implementation defects. Finding 3 correctly identifies a missing client guard, but the claimed account-wide wipe is not established: pCloud documents error `2007` for attempts to delete the root. The client now rejects root IDs before making a request and uses server-enforced empty-folder deletion instead of recursive deletion. See [deletefolderrecursive](https://docs.pcloud.com/methods/folder/deletefolderrecursive.html) and [deletefolder](https://docs.pcloud.com/methods/folder/deletefolder.html).

Two other corrections affect the proposed remedies and readiness claim:

- Corrupt encrypted preferences must **not** be deleted to recover startup. The implementation preserves the original encrypted store, selects a fresh encrypted store when possible, and fails closed if secure storage remains unavailable. Individual corrupt values return no credentials and require reconnection.
- The runtime login uses `response_type=token`, not an authorization-code PKCE exchange. The PKCE helper and state checks do not establish PKCE interception protection for this runtime flow. Account identity is now verified using authenticated `userinfo` before an atomic session save. The report's “100% safe” statement is unsupported.

## Operational changes and recovery

- Use dedicated, separate cloud folders and non-overlapping local roots. Existing invalid/root/overlapping pairs stop instead of syncing. Stored cloud names can become stale after rename; the ID remains authoritative.
- Local overwritten/deleted versions are retained under each pair's `.relayfs-recovery/`, with `.path` sidecars identifying their original relative paths. Cloud versions are copied into account-root `.relayfs-recovery` before mutation; names include source ID and original-name prefix. Copies consume storage and are not automatically purged. Preservation failures stop the affected mutation.
- Failed/interrupted virtual-drive edits remain in persistent app-private storage and appear on the dashboard. Export creates a copy and retains the original. Retry is explicit for interrupted edits; discard requires UI confirmation and refuses an actively open descriptor. Uninstall or clearing application storage removes these app-private edits, so export them first.
- Unknown legacy account identity intentionally blocks syncing. Removing pairs does not delete their local/cloud user files. Export pending edits and review/export conflict branches before removing old configuration, reconnect to verify identity, then recreate pairs. Local/cloud bytes are compared conservatively on the first pass.
- File rename through SAF uses non-overwriting cloud copy followed by preserved, checked source deletion. A failed final step may leave two copies. Recursive directory deletion is disabled; nonempty folders are rejected by the server.
- The mass-deletion guard has fixed conservative limits. Review both endpoints, recover unintended removals, or deliberately reconfigure the pair after review; there is no automatic bulk-delete override.

## Remaining limits and live acceptance gates

1. **External writer race:** another app/device can change a file between the final version check and the local rename or remote upload/delete request. Independent recovery copies cover versions captured before mutation, but cannot guarantee capture of an external edit that arrives in that last interval. pCloud's documented upload/rename/delete methods do not offer a revision-match conditional mutation; atomic POSIX rename alone is not conditional either. When cloud hashes are unavailable, comparison falls back to size/mtime, which also has timestamp granularity limits. This is not a zero-data-loss guarantee. See [uploadfile](https://docs.pcloud.com/methods/file/uploadfile.html), [copyfile noover](https://docs.pcloud.com/methods/file/copyfile.html), and [renamefile overwrite behavior](https://docs.pcloud.com/methods/file/renamefile.html).
2. **Physical interruption and flash durability:** JVM tests exercise interrupted journal states and cancellation, not power loss at every filesystem/SQLite boundary, OEM Keystore behavior, or real SAF clients. Files are fsynced, but directory-entry durability and emulated-storage behavior still require device testing.
3. **Live acceptance:** test the corrected build against a disposable dedicated pCloud folder and copied local documents. Exercise rename/move/removal, concurrent edits, small/large transfer interruption, offline SAF writes, process kill before/after descriptor close, recovery export/retry, conflict choices, and upgrade from the currently installed database. Verify recovered bytes, not only success counts. Do this before entrusting sole copies of real data.
4. **Release gate:** the assembled release APK is unsigned. Configure production signing and verify the signed release on the target Android device. No device instrumentation or live OAuth/cloud acceptance was performed during this remediation. The runtime client ID still requires the existing pCloud developer configuration; no mock runtime credentials were added.

These are explicit acceptance limits, not hidden successful checks. Keep independent backups through controlled validation and initial use.
